# pihole

[Pi-hole](https://pi-hole.net/) — the LAN's DNS resolver at `https://dns.dahub.casa`. Every device
in the house resolves through it, so advertising and telemetry are filtered **at the network
layer** (including on devices that can never run a blocker), every query is attributed to a client,
and `*.dahub.casa` resolves to the LAN address at home instead of detouring through the Tailscale
mesh ([ADR-0014](../../docs/decisions/0014-pihole-as-lan-dns-resolver.md)).

## Quick reference

| Field         | Value                                          |
| ------------- | ---------------------------------------------- |
| Image         | `pihole/pihole:2026.07.2`                      |
| URL           | `https://dns.${DOMAIN}` (via Caddy; DNS itself on `:53`) |
| Port          | 53/udp + 53/tcp, bound to `${HOST_IP}` and `${TAILNET_IP}` only — never `0.0.0.0` |
| Networks      | `proxy`                                        |
| Config path   | — (single app dir; see Data)                   |
| Data path     | `${DATA_ROOT}/pihole` (config + gravity + query history, single mount — documented deviation) |
| Backup        | yes — settings, blocklists and local DNS records exist **only** here, not in Git |
| Category      | infrastructure                                 |

## Deviations from the standards

- **Published port (rule 6 — the case the rule provides for):** DNS/UDP cannot traverse an HTTP
  reverse proxy, so this service publishes `53`. It is **not** an architectural exception: the bind
  is scoped to the LAN and tailnet addresses, so the bind address itself is the boundary and no
  host firewall rule exists (unlike NetAlertX's port 20211). Recorded in
  [ip-plan](../../docs/network/ip-plan.md); annotated in `compose.yaml`.
- **Single mount:** Pi-hole v6 keeps `pihole.toml`, `gravity.db` and `pihole-FTL.db` all under
  `/etc/pihole`, collapsing the two-mount rule into one — same situation as vaultwarden, documented
  as a comment in `compose.yaml`, no ADR.
- **Variable naming:** `FTLCONF_*` names are canonical upstream (they mirror `pihole.toml` keys)
  and are kept verbatim, case included — the same documented deviation as `CLOUDFLARE_API_TOKEN`
  in [`services/caddy`](../caddy/README.md).

## Dependencies

- `proxy` network + Caddy with TLS ([ADR-0011](../../docs/decisions/0011-dns-01-tls-certificates.md))
- `HOST_IP` and `TAILNET_IP` **non-empty** in the root `.env` — an empty value silently degrades the
  bind to `0.0.0.0` (caught by `docker compose config` in the runbook)
- Port 53 free on those addresses: `systemd-resolved`'s stub listener must stay on `127.0.0.53`
- Router access, to point the DHCP DNS option at the host
- Uptime Kuma deployed, so this service is monitored from day one

## Configuration

- Environment: globals via the `.env` symlink ([ADR-0012](../../docs/decisions/0012-layered-environment-files.md));
  service layer in [`.env.service.example`](.env.service.example) — copy to `.env.service`
  (`chmod 600`) and set the admin password. Non-secret `FTLCONF_*` settings live in `compose.yaml`.
- Upstream resolvers default to Cloudflare (`1.1.1.1`, `1.0.0.1`) and are changeable from the UI.
- **Blocklists and local DNS records are configured in the web UI**, not in Git. They persist under
  `${DATA_ROOT}/pihole` and are therefore backup-dependent state — see Data.

Details: [`docs/`](docs/README.md).

## Data

`${DATA_ROOT}/pihole`:

| File            | What it is                                | If lost                          |
| --------------- | ----------------------------------------- | -------------------------------- |
| `pihole.toml`   | All settings, incl. local DNS records     | Re-run setup by hand             |
| `gravity.db`    | Compiled blocklists                       | Regenerated by updating gravity  |
| `pihole-FTL.db` | Query history, per client                 | History gone; service unaffected |

Small (tens of MB; the query DB grows with a rolling retention window). `pihole-FTL.db` is a
**per-client record of household browsing** — the most privacy-sensitive data on the platform.

## Backup & restore

- SQLite: dump or stop-copy-start, never a live file copy
  ([execute-backup](../../docs/runbooks/execute-backup.md)); `pihole.toml` rides the file backup.
- Restore: [restore-from-backup](../../docs/runbooks/restore-from-backup.md). After a restore,
  verify the **local DNS records** survived — they live in `pihole.toml` and nowhere else.

## Operations

- Health: `docker compose ps` → `healthy`; `dig +short cloudflare.com @192.168.100.17` resolves
- Logs: `docker compose logs -f pihole`
- Known failure modes:
  - **The whole house loses DNS** → this service is a single point of failure by design
    ([ADR-0014](../../docs/decisions/0014-pihole-as-lan-dns-resolver.md)). First response is not to
    debug the container: set the router's DNS option back to `1.1.1.1`, then investigate.
  - Container won't start, `:53` already in use → `systemd-resolved`'s stub listener went global,
    or the bind fell back to `0.0.0.0` because `HOST_IP`/`TAILNET_IP` are empty
  - Container won't start after a reboot → the `${TAILNET_IP}` bind fails while `tailscale0` has no
    address yet; `restart: unless-stopped` retries
  - Queries attributed to a Docker gateway address instead of the real client → `userland-proxy`
  - A site is broken → check *Query Log*, allowlist the domain; do **not** disable filtering wholesale
  - Remote access to `*.dahub.casa` broken → a tailnet device was pointed at Pi-hole and got the LAN
    address from the split-horizon record. See the ADR: this is why Pi-hole is not the tailnet's
    global nameserver.
